# 運用・復旧

## メール・決済の監視

- `/admin/operations` で未送信注文を確認。失敗と10分以上停止した送信中注文は再試行可能。
- メール送信はResendの `ticket-email/<orderId>` 冪等キーを利用。キーは24時間有効。24時間超の再試行は送信履歴を確認し、重複配信に注意する。
- 未送信が増えたらResendの送信元認証、利用制限、配信ログとホスティングログを確認。SENTはAPI受付済みで、受信箱への配信保証ではない。
- Stripe Dashboardで失敗Webhookを監視し、原因修正後に再送。署名キーと本番/テストの環境を取り違えない。
- ホスティング側で5xx増加と `Webhook processing failed` / `Ticket email failed` の通知を設定。通知の接続先は外部管理画面で設定する。
- 同時に複数の手動再送を始めない。メール文面や公開URLを変更した直後は、同じ冪等キーの再送内容と一致しないことがある。

## 満席時

現在は管理者がmicroCMSのイベントstatusを `sold-out` に変更して販売停止する運用。自動在庫予約・定員制御は未実装。
新規購入APIは停止するが、すでに作成されたStripe Checkout Sessionは残るため、Stripe側でも対象の未完了セッションを期限切れにする。
厳密な定員保証が必要なイベントでは、自動予約・決済期限との連動を実装してから販売する。

## バックアップ

`npm run db:backup` はDIRECT_URL優先で読み取り専用のpg_dumpを実行し、`.local/backups` に権限0600のcustom形式を保存。
pg_dumpを事前インストールし、Postgresのサーバーバージョンと互換性のあるものを使う。
接続資格情報はコマンド引数・ログへ出さない。バックアップには個人情報が含まれるため暗号化した別保管先へ保存する。
バックアップ頻度・保管期間・管理責任者を決め、ホスティング/DBサービスの自動バックアップも有効にする。

## 復旧訓練

1. 本番と別の空のDBを作成する。本番接続情報は使用しない。
2. `pg_restore --list <backup.dump>` で内容を確認する。
3. 復旧先専用のPGHOST/PGPORT/PGDATABASE/PGUSER/PGPASSWORD/PGSSLMODEを設定し、`pg_restore --no-owner --no-privileges --dbname="$PGDATABASE" <backup.dump>`。
4. 件数、注文・チケットの関連、使用済み/返金済み状態、マイグレーション履歴を確認する。
5. 復旧先アプリは外部メール・決済に接続しない設定で確認する。バックアップ由来の有効チケットを外部に公開しない。

## ロールバック

今回のDB変更は新テーブル・nullable列の追加で、データの削除は含まない。旧版へ戻す場合も追加列・テーブルを即削除しない。
購入・発券を停止し、Stripeの支払い済みセッションと注文の照合後に再開する。DBの巻き戻しだけではStripeの決済は戻らない。
